## 已核实的实现

- 新管理端点均检查管理员角色，读写服务再次检查 actor。嵌套家长详情、编辑、主要联系人操作均核对目标家长的所属学生。普通学生编辑只提取允许字段，不能改变学籍、归档标记和账号。
- 单次写操作的业务变更与审计由同一路由事务提交。单请求切换主要家长时先取消并刷写原主要，再设置新主要。现有测试使用真实数据库触发器覆盖审计失败后的业务回滚。

## Critical

1. **并发学籍操作可撤销毕业并产生矛盾审计。** `app/services/student_service.py:64`、`app/services/student_service.py:67` 按当前会话缓存校验后，无条件写入新状态。临时库中 A 读取在读学生，B 迁移到毕业并提交，随后 A 办理休学也提交成功。最终是休学，日志的连续两条记录却为「在读→毕业」「在读→休学」。应在同一事务内对真实原状态做条件更新并检查影响行数，或在业务读取前准备串行化写事务并刷新缓存。冲突必须停止提交，并保留胜出操作的审计。

## Important

1. **并发设置主要联系人会报告未生效的成功。** `app/services/parent_service.py:61` 根据缓存中的 `is_primary` 提前返回。临时库中 A 已读取主要家长 1，B 切换到家长 2 并提交，再在 A 办理设 1 为主要，调用成功，数据库所存主要联系人仍为 2。应使目标读取、旧主要解除、新主要设置和两条审计处于同一受保护的写事务。幂等判断也应核对事务内的最新状态。
2. **确认框显式为假仍能办理归档。** `app/admin/archive_forms.py:51` 使用 `InputRequired` 检查原始输入是否存在。临时库中以真实令牌提交 `confirm=false`，表单布尔值实际为假，响应为 303，学生被归档。恢复和设主要联系人复用该表单。应验证解析值确为真，并测试缺少、显式否定以及正常勾选三种情况。
3. **家长全局列表在继续搜索时丢失已选学生。** `app/admin/parent_routes.py:15`、`app/templates/admin/list.html:15`。从全局页选择学生后，响应中的查询表单只包含 `q` 和 `per_page`。继续搜索时浏览器重建查询串，全校同名家长会重新进入结果。应保持学生选择器及其选中值，或将已选范围固定在嵌套路径。建议使用不同学生、同名家长验证第二次搜索的结果。

## Minor

1. **分页读额外加载三个完整档案表。** `app/services/archive_references.py:11`、`app/admin/student_routes.py:26`、`app/admin/parent_routes.py:15`。即使学生列表每页只显示一条，仍将全校学生、教师、班级档案构造成 ORM 对象；嵌套家长页根本没有选择器，也执行这些查询。按页面实际使用的单一实体查询所需 ID 和标签列即可。
2. **服务直接接收空班级筛选时抛出意外异常。** `app/services/student_service.py:88`。临时库调用 `list_students(admin, class_id="")` 得到 `AttributeError`，因为可空关联解析得到 `None` 后仍访问其主键。HTTP 入口先将空值归一化，所以常规浏览器操作不受影响。服务应把空筛选归一化为全部，或返回领域校验错误。
3. **合法的大主键不能用于筛选。** `app/admin/archive_views.py:30` 将班级及学生过滤 ID 与页码一同限制为 2147483647，而领域服务和 SQLite 主键支持到 9223372036854775807。已有高位 ID 的学生或班级可以打开详情，在筛选器里选择它却返回 400。应分别解析分页和实体 ID，保留两者各自的上限。
